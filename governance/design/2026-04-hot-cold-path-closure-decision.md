# 热冷路径收口决策

## 目的

这份决策稿只回答一个问题：

**`graduate-thesis-review` 的默认热路径应该最小化到哪些模块，哪些模块降为冷路径，以及在不删除机器合同的前提下如何收口。**

本稿不修改 `SKILL.md`，不改 `scripts/`，不改 `evals/`，也不要求删除现有 reference。它只定义收口原则和触发边界，供后续入口层和工作流层对齐。

## 决策

### 1. 默认热路径收窄

默认热路径只保留审查工作必需的最小核：

1. 研究问题与证据边界判断
2. 专业领域路由
3. 专项手册完备性判断
4. 运行架构与证据投影的最小映射

默认不把以下能力放进热路径：

1. 导师式逐段改稿
2. 前沿检索与创新定位
3. 深审加闸
4. 多角色协作适配
5. 形式审查全量清单

### 2. 冷路径只在触发时加载

所有冷路径模块都必须满足“有明确触发条件、产物可回收、不会改写机器合同”。

冷路径不等于不重要，只表示它不是每次审查都应默认加载的心智负担。

### 3. 机器合同不删除，只降默认可见度

收口的核心原则是：

1. 机器合同继续保留
2. 机器合同继续作为运行真源
3. 机器合同不再默认进入用户心智热路径
4. 对外输出只暴露必要的投影，不暴露全部中间合同

也就是说，收口的是默认激活面，不是治理能力本身。

## 收口原则

### 原则 A: 热路径只保留“每次都要用”的模块

如果一个模块只在少数论文类型、少数阶段或少数输出形态下才需要，就不应进入默认热路径。

### 原则 B: 冷路径必须有显式触发条件

每个冷路径模块都要能回答以下至少一个问题：

1. 论文类型是否触发
2. 用户意图是否触发
3. 输出形态是否触发
4. 风险等级是否触发

### 原则 C: 合同保留，默认不扩散

以下资产属于机器合同或合同性中间层，必须保留：

1. runtime / workflow 真源
2. evidence / verdict / limitation 一类结构化对象
3. output policy / projection contract 一类授权边界
4. 专项 gate 与专业路由的可验证规则

这些资产可以不在默认入口层全部展开，但不能因为收口而删除或弱化。

### 原则 D: 设计稿只定义边界，不替代执行

这份文档只定义：

1. 哪些模块默认热
2. 哪些模块默认冷
3. 冷模块何时激活
4. 机器合同如何保留

它不替代工作流实现，也不替代测试验收。

## 默认热路径

默认热路径建议只保留以下 4 个核心模块：

1. `references/review-rubric.md`
2. `references/specialty-router.md`
3. `references/specialty-manual-readiness-gate.md`
4. `references/review-operations-architecture.md`

这 4 个模块足够支撑：

1. 基础审查标准
2. 专业识别
3. 专项完备性判断
4. 运行对象与投影关系

## 冷路径

冷路径模块按触发加载，不进入默认热路径。

1. 形式审查类模块
2. 导师修改类模块
3. 前沿检索类模块
4. 深审与跨代理复核类模块
5. 专项细则类模块
6. 展示投影类模块

## 触发规则

1. 当任务进入送审、预答辩、正式答辩前终稿时，才激活形式审查类模块。
2. 当用户明确要求建设性建议、学生执行清单、逐段改稿时，才激活导师修改类模块。
3. 当用户要求创新性、最新进展、领域定位、高水平导师判断时，才激活前沿检索类模块。
4. 当研究类型复杂、结论横跨多个闭环、或不同意见发生冲突时，才激活深审与跨代理复核类模块。
5. 当专业已识别且专项完备性不足时，才激活专项细则类模块。
6. 当任务明确进入网页、HTML、display_projection 时，才激活展示投影类模块。

## 验收标准

收口是否成立，至少看四件事：

1. 默认热路径是否能被一句话说清
2. 冷路径是否都有明确触发条件
3. 机器合同是否继续保留
4. 默认心智负担是否明显下降

如果任何一个冷模块仍然被当作默认入口层的一部分，说明收口没有完成。
