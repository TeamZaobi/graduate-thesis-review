# 产出模板

当需要把论文审查结果落成具体交付物时，加载此文件。默认以中文交付为主；若原文是英文论文，也优先用中文给出判断和执行建议，除非用户明确要求英文版成品。

当前优先级说明：

1. `evidence/review-verdict.json + knowledge/output-policies/advice-output-policy.json`
   - 控制 `导师/学生` 高风险输出是否允许出现
2. `notes/legacy-review-manifest.json.release_gate + notes/评审闭环与放行判断.md`
   - 当前只保留 readiness 等 legacy 兼容语义

后文如继续出现 `reviews/review_version_manifest.json` 或 `reviews/评审闭环与放行判断.md`，默认把它理解为 `notes/` canonical 文件的兼容 alias。

## 0. 先出证据型中间产物，再出总结材料

复杂或高风险论文，不要一上来只写综合报告。先产出并实填证据型中间文件，再汇总成最终交付物。

常用的证据型中间文件包括：

- `notes/process_projection.md`
- `notes/legacy-review-manifest.json`
- `notes/评审闭环与放行判断.md`
- `方法学修复路径表.md`
- `导师分层修改建议.md`
- `流调统计语言校准表.md`
- `audience_language_contract.md`
- `display_projection_schema.md`
- `审阅对象冻结说明.md`
- `版本冻结与依赖回归台账.md`
- `关键数值与复算准入台账.md`
- `图表索引台账.md`
- `图表专项核查.md`
- `核心结果证据链表.md`
- `目标试验与因果识别审计表.md`
- `伦理合规与数据追溯审计表.md`
- `主文补充附录交叉索引台账.md`
- `文献对标与引文法证.md`
- `上下文隔离反思.md`
- `局部改写任务卡.md`

这些文件不要求每篇论文全开，但至少要覆盖本轮最主要的风险源。空模板、只写标题的骨架文件，不算“已完成审查”。
如果文件来自 `init_review_workspace.py` 的默认脚手架，先清掉 `tainted` 标记，再把它视为可交付对象。

`legacy-review-manifest.json` 当前最少要能回答：

- 这次进入工作区的 `entry_mode` 是什么
- 当前唯一审阅对象和真源是什么
- 历史版本、废弃锚点和 rebase 状态是什么
- 当前 slow variables 和 dependents 是什么
- 当前工作区 readiness 处于 `blocked / partial / ready` 哪一档
- 当前 `release_gate` 是否允许问题清单和 readiness 兼容语义

如果论文高度依赖图、表、引文或多线程接手，再补对象层真源：

- `objects/figures.json`
- `objects/tables.json`
- `objects/citations.json`
- `objects/assets_manifest.json`

这些对象文件不是展示页，也不是长文台账，而是供后续台账、HTML 和回归检查复用的结构化上游。

如果图件是关键证据，先把来源类型写清：

- `objects/figures.json` 至少区分 `docx_media` 和 `shape_rendered`
- `objects/assets_manifest.json` 至少区分 `source_kind` 和 `asset_type`
- 不要把页图、裁图或重导出页图直接伪装成“从源抽出的原图”

## 0.1 学科语域先于展示润色

对导师、学生、网页页面和正式评审摘要，先继承专项阶段已经确认的学科语域，再谈展示结构或措辞润色。

默认规则：

- 先看 `专业手册完备性判断.md` 里记录的学科语域和替换词
- 如果 `discipline_register_status = partial / missing`，先补 `专业专项补充说明.md` 中的本学科推荐用语
- 对外交付物不要直接沿用 Skill 内部工作语言
- 文件名暂因兼容性保留旧名时，正文标题、页面标题和链接文字也应优先翻译成学科可接受表述

## 1. 分阶段交付组合

在证据型中间文件已有实填内容后，不要立刻把审查结果包装成执行面。完整审查默认分两段交付：

### A. 评审进行中可产出

- `论文多智能体审查报告.md` 或同等综合报告
- 证据型台账、问题映射、问题清单
- 入口页、问题清单页、完整评审页等当前状态展示页

这阶段可以明确“问题有哪些、证据在哪、还缺什么”，但不要默认下发：

- `最终可执行修改清单.md`
- `学生执行版修改清单.md`
- `导师汇报版摘要.md`
- `display/学生执行页.html`
- `display/导师汇报页.html`
- “建议送审 / 建议答辩”的最终判断

### B. 评审闭环后可产出

只有先满足两条条件，才默认补执行或决策型材料：

1. `review-verdict + output policy` 已允许对应 advice/student outputs
2. 如需送审 / 答辩判断，再补 `notes/评审闭环与放行判断.md` 并同步更新 `legacy-review-manifest.json.release_gate`

legacy gate 至少明确：

- `can_emit_execution_outputs = yes`
- `can_issue_readiness_verdict = yes` 或明确为 `no`
- `can_enter_line_editing = yes` 或明确为 `no`

才默认补以下执行或决策型材料：

1. `最终可执行修改清单.md` 或同等行动清单
2. `学生执行版修改清单.md`
3. `导师汇报版摘要.md`
4. 一套 display_projection 展示层页面中的学生执行页 / 导师汇报页
5. 必要时给出送审 / 答辩 readiness 判断

如果进入网页 / HTML 交付模式，完整放行后默认至少包含以下五个页面文件：

- `综合评审汇总.html`：入口页 / 导航页 / 当前状态总览
- `display/问题清单页.html`
- `display/完整评审页.html`
- `display/学生执行页.html`
- `display/导师汇报页.html`

除非用户明确要求只做单页且项目极轻，否则不要把这四类页面压成一个 HTML。

如果用户明确要求导师视角、逐条修改建议或可直接替换的文字版本，再补：

- `方法学修复路径表.md`
- `导师分层修改建议.md`
- `流调统计语言校准表.md`
- `原子级修改建议.md`
- `论断-引文核查表.md`
- `证据绑定改写表.md`

如果用户要求判断“创新性 / 最新进展 / 领域定位 / 答辩中的前沿说法”，再补：

- `前沿知识简报.md`
- `创新定位判断卡.md`

如果完整评审尚未闭环，但只允许处理用户明确指定的局部高风险段落，此时不要直接打开上述全文改稿材料；只允许补：

- `legacy-review-manifest.json.task_exceptions.scoped_rewrite`
- `notes/局部改写任务卡.md`

如果论文进入“强制深审”模式，建议再固定补三份证据型材料，或将其合并为综合报告附录：

- `核心结局证据链表.md`
- `干预与对照矩阵.md`
- `图片法证核查.md`

如果 workflow 很复杂，或论文经历了多轮改稿、多代理协作、摘要结论反复漂移，再优先补以下治理型文件：

- `process_projection.md`
- `review_version_manifest.json`
- `评审闭环与放行判断.md`
- `audience_language_contract.md`
- `display_projection_schema.md`
- `审阅对象冻结说明.md`
- `版本冻结与依赖回归台账.md`
- `关键数值与复算准入台账.md`
- `主文补充附录交叉索引台账.md`
- `伦理合规与数据追溯审计表.md`
- `文献对标与引文法证.md`

如果图表问题或答辩问题特别重，再补：

- `图片专项修改清单.md`
- `答辩口径.md`
- `第三方建议复核意见.md`

## 2. 建议同时拆出两份轻量材料

当完整版开始超过普通修改者的阅读负担时，建议同步拆出：

### A. 学生执行版

只保留：

- 当前必须改什么
- 顺序怎么排
- 每一项的完成标准
- 每一项依据哪条方法学判断
- 每一项是否还需人工回查
- 每一项属于 `L1 / L2 / L3 / L4` 哪一层

不要在学生版里堆过多背景论证。
学生版的标题和段落名应使用学科常用审查语言，不要把工程隐喻直接暴露给学生。

### B. 导师摘要版

只保留：

- 论文当前定位
- `P0` 的数量和最关键几条
- 放行后才写“是否建议答辩 / 是否建议送审”；未放行时明确写“评审进行中 / 暂不放行”
- 最值得保留的主线
- 最该收紧的结论
- 分层后的导师投入回报判断（哪些属于 `L1-L4`）
- 必要时补一句创新定位是否需要重写

导师版的目标不是“教学生怎么改”，而是让导师 1 分钟内知道决策重点。
导师版的页面标题、问题标签和决策句，也应优先使用该学科自然表述，而不是工作流黑话。

## 2.5 网页多页投影模板

只要用户要求网页、HTML、完整评审展示、学生页、导师页，或明确说“不要只报问题，要有完整结果”，默认做多页投影，不要把所有内容混在一页。

开始写网页前，先固定检查一份放行判断，再补两份合同文件：

- `notes/评审闭环与放行判断.md`

- `reviews/audience_language_contract.md`
- `reviews/display_projection_schema.md`

没有这份放行判断和两份合同文件，不要直接开始写入口页或四个子页。

### 2.5.1 `audience_language_contract.md`

最少字段：

- 页面名
- 论文所属学科
- 目标读者
- 使用场景
- 本学科常用审查用语
- 应避免的跨学科行话
- 允许出现的术语
- 禁止直接出现的内部术语
- 首层应该保留的判断
- 页面阅读规则
- 适合写成 `tips` 的内容
- `tips` 不应承担的内容
- `drilldown` 标题与展开方式
- 不应在该页承担的职责

用途：

- 防止把内部工作语言直接写到成品页
- 防止学生页、导师页、完整评审页混用同一种语气
- 防止把软件工程、数据工程和项目管理行话误投到非工程学科交付物

### 2.5.2 `display_projection_schema.md`

最少字段：

- 页面名
- 页面目标
- 目标读者要做出的判断
- 首层必须承载的判断
- `tips` 需要承载的阅读规则
- `drilldown` 需要承载的深层依据、例外或阻塞项
- 必须出现的内容块
- 不应出现的内容块
- 上游依据文件

用途：

- 先定义“该页需要哪些评审内容”，再决定展示结构
- 防止只扩 `tips` / `drilldown` / tab / 流程图，却没有真正补充完整评审结果

### 2.5.3 多页网页的默认三层

五个页面默认都按三层写：

1. 首层：当前判断、问题本体、动作本体
2. `tips`：阅读规则、边界条件、先看什么、哪里容易误读
3. `drilldown`：证据链、例外、阻塞项、深层依据

执行规则：

- `tips` 和 `drilldown` 默认是标配，不是装饰项
- 如果一页写不出合理的 `tips`，先回头检查阅读规则是否还没提炼出来
- 如果一页写不出合理的 `drilldown`，先回头检查证据深度是否还没沉下去
- 但首层正文不能被 `tips` 或 `drilldown` 取代

### A. 入口页 `综合评审汇总.html`

作用：

- 给出总导航和当前状态
- 明确当前评审状态；只有放行后才写本轮是否建议送审 / 答辩
- 链接到四个子页

入口页至少包含：

- 当前总体判断
- 本轮审阅边界
- 关键计数或风险级别
- 四个子页入口
- 更新日期 / 当前版本说明
- `tips`：告诉读者这页先看什么、当前放行边界是什么、有哪些特殊判读规则
- `drilldown`：承载关键状态依据、例外说明和页面导航背后的深层信息

### B. 问题清单页 `display/问题清单页.html`

作用：

- 按 `P0 / P1 / P2 / P3 / P4` 集中展示问题
- 让读者快速定位“问题是什么、证据在哪、该怎么改”

至少包含：

- 优先级矩阵
- 全量问题卡片
- 每条问题的 `定位映射 / 证据 / 为什么危险 / 安全修法 / 答辩追问点 / 确认状态`
- 图表问题对应的关键缩略图证或页图
- `tips`：告诉读者先看哪些级别、哪些问题不能按普通排版错误理解
- `drilldown`：为关键问题或关键证据提供展开层，而不是只有卡片摘要

不要承担：

- 全部 workflow 叙述
- 面向学生的逐项执行清单
- 面向导师的高层决策摘要

### C. 完整评审页 `display/完整评审页.html`

作用：

- 呈现完整评审判断，而不只是问题清单
- 给出从当前评审状态到逐项核查、图表专项、剩余评审步骤或放行后执行顺序、以及终检的全貌

至少包含：

- 总体判断
- 当前评审状态；只有放行后才写送审 / 答辩 readiness
- 审阅步骤或 workflow
- 逐项核查结果
- 图表专项或关键证据入口
- 剩余评审步骤或放行后的执行顺序
- 交稿前终检
- `tips`：明确阅读顺序、评审边界和特殊对象的判读方法
- `drilldown`：承载 workflow 细节、逐项核查依据、阻塞项和例外说明

这是多页网页里的主页面；如果只能精修一页，优先精修这一页。

### D. 学生执行页 `display/学生执行页.html`

作用：

- 把复杂审查结果翻译成学生当前能执行的动作

前提：

- 只有 `评审闭环与放行判断.md` 明确 `can_emit_execution_outputs = yes` 时才产出本页

至少包含：

- 当前必须修改的事项
- 修改顺序
- 每项完成标准
- 仍待人工回查的材料
- 明确禁止做什么
- `tips`：明确先后顺序、完成标准和常见误操作
- `drilldown`：解释每个动作为什么现在做、卡在哪里、需要补什么材料

不要放：

- 过长的背景论证
- 导师决策口径
- 超过执行所需的长篇方法学解释

### E. 导师汇报页 `display/导师汇报页.html`

作用：

- 让导师在最短时间内看到决策重点

前提：

- 只有 `评审闭环与放行判断.md` 明确 `can_emit_execution_outputs = yes` 时才产出本页

至少包含：

- 当前论文定位
- 只有放行后才写是否建议送审 / 是否建议答辩
- 最高风险项
- 当前可以保留的主线
- 最需要收紧的结论
- 关键决策点与答辩口径
- `tips`：明确导师先看什么、哪些判断仍在评审中、哪些内容不是本页重点
- `drilldown`：展开最高风险项、主线保留理由和拍板依据

不要放：

- 学生逐条执行细节
- 全量问题卡片
- 大段证据型台账正文

### F. 多页网页与轻量文档的共同上游

四个子页以及 `学生执行版修改清单.md`、`导师汇报版摘要.md` 不能各写各的。生成前先建立一份共享的问题映射台账或等价结构，至少包含：

- `问题 ID`
- `级别`
- `定位映射`
- `证据路径`
- `为什么危险`
- `安全修法`
- `确认状态`
- `受众落点`

`受众落点` 至少标明该问题应该进入：

- 问题清单页
- 完整评审页
- 学生执行页
- 导师汇报页

没有进入共享映射的问题，不要直接写入某个网页子页或轻量 Markdown。

`评审闭环与放行判断.md`、`audience_language_contract.md` 和 `display_projection_schema.md` 也应与这份共享映射共同维护；如果其中一份改了，相关网页子页和轻量文档都要同步回查。

## 3. 综合报告模板

建议结构：

### A. 总体判断

- 这篇论文现在能否答辩 / 送审？
- 最关键的 `3-5` 条理由是什么？

### B. 多角度发现

只有在有帮助时才按镜头展开。常用镜头：

- 流行病学
- 统计学
- 学术写作
- 工程实现
- 康复科学
- 神经科学

每条发现尽量包含：

- 问题是什么
- 原文或图表定位
- 为什么有风险
- 建议怎么改
- 是否已确认 / 仍待核实

如果属于临床干预 / 康复工程深审，建议在综合报告中专设一节“证据链附录”，最少包括：

- 核心结局证据链表
- 干预与对照矩阵
- 工程可复现性矩阵
- 图片法证结论

### C. 共识结论

总结多角度复核最终都指向了什么。这部分通常最能揭示真正的瓶颈。

## 4. 执行清单模板

固定按优先级结构写：

### `P0`

- 阻止安全送审或答辩的问题
- 每条都要写清楚到底要统一、补充、重算、还是收紧

### `P1`

- 高概率被追问、会明显拉低严谨度的问题

### `P2`

- 方法与报告规范加固

### `P3`

- 清稿、展示、术语、编号、格式与交付回归

### `P4`

- 外审 / 答辩防守增强，不造新事实

### `Strategy`

- 高回报答辩增强，不补造事实

### `Upgrade`

- 下一轮研究或投稿导向的结构升级

每条尽量按这个小结构写：

1. 问题
2. 为什么危险
3. 安全修法
4. 明确禁止做什么

对进入强制深审的论文，`P0` 部分优先按这几个源头归类，避免只写零散问题：

1. 研究身份与样本流程
2. 核心结局证据链
3. 干预与对照可信度
4. 图片语义与统计呈现

## 4.5 导师式逐条改稿模板

当用户要的是“直接怎么改”，不要把完整版评审长文简单换个标题。至少输出一组逐条修改卡片。

推荐卡片字段：

1. `定位`
2. `原句 / 原段`
3. `问题类型`
4. `修改目标`
5. `证据锚点`
6. `建议改写`
7. `禁止改法`
8. `是否需人工回查`

推荐问题类型：

- 结论过强
- 结果句不对表
- 统计表述不严谨
- 引文不匹配
- 术语不稳
- 章节错位
- 图题 / 表题不准确

如果用户要“可直接替换文本”，也必须保留 `证据锚点` 和 `禁止改法`，不要只给改写句。

对 `DOCX` 终稿精修，建议再补一个按章节汇总的版本：

- 摘要精修
- 方法精修
- 结果精修
- 讨论精修
- 结论精修

## 5. HTML / 网页展示模板

HTML 的目标是：准、全、能跳转、能打印、能共享。对“强制深审”项目，网页默认不是简短概览，而是“入口页 + 多个子页”的证据工作台。

先确认前置证据文件已经实填，再生成网页。不要让网页代替尚未完成的图表核查、版本冻结或结果依据核实。

生成网页前，先整理一份“问题映射台账”，至少包含：

- `问题 ID`
- `级别`
- `原文或图表定位`
- `证据路径`
- `为什么危险`
- `安全修法`
- `答辩追问点`
- `确认状态`

没有进入台账的问题，不要直接写进网页；未核实但必须提醒人工回查的点，统一标成 `待人工回查`。

同时检查两份展示层合同文件是否已实填：

- `audience_language_contract.md`
- `display_projection_schema.md`

如果图像和表格资产已经对象化，优先从 `objects/assets_manifest.json`、`objects/figures.json` 和 `objects/tables.json` 生成网页中的证据路径、图号和 caption，不要在 HTML 里手写绝对路径。

建议分工：

1. 入口页：总览与导航
2. 问题清单页：优先级矩阵 + 问题卡片
3. 完整评审页：workflow + 逐项核查 + 图表专项 + 剩余评审步骤或执行顺序 + 终检
4. 学生执行页：动作清单 + 顺序 + 完成标准
5. 导师汇报页：高层判断 + 关键决策 + 风险摘要

制作网页时要注意：

- 锚点稳定，不要频繁改 `id`
- 数量指标要和正文同步
- 卡片可以紧凑，但不能牺牲证据映射；避免把大段背景论证原样塞进网页
- 图像问题直接给本地图证、页图或裁图，不要只放“入口”
- 非图像问题也要给原文定位、摘录或行号，不能只写抽象结论
- 完整评审页中的终检模块必须存在，否则它只是“诊断书”，不是“完整评审页”
- 四个子页必须边界清楚，不能只换标题不换内容

问题卡片固定结构：

1. `问题 ID + 级别`
2. `定位映射`
3. `证据展示`
4. `为什么危险`
5. `安全修法`
6. `答辩追问点`
7. `确认状态`

覆盖规则：

- `P0 / P1 / P2` 每条都要有对应卡片
- 当问题总数 `<= 15` 时默认全部展开，不要只留摘要面板
- 当问题总数 `> 15` 时，至少 `P0 / P1` 全展开，`P2` 可折叠
- 图表问题必须展示关键缩略图证或页图
- 非图表问题必须能追溯到原文、表格、文件行号或其他本地证据
- 如果某条问题仍依赖学生回查原始记录，卡片里要明确写出“待人工回查什么”

如果属于强制深审项目，完整评审页中至少要能看见：

- 深审触发原因
- 哪些问题由哪个 agent / 专家镜头确认
- 核心结局证据链摘要
- 图片法证摘要和关键缩略图证

生成完成后，至少补跑一次网页交付回查：

- 入口页统计、问题清单页矩阵、问题卡片数量是否和综合报告、清单一致
- 每张卡片是否都保留了 `定位映射 / 证据 / 为什么危险 / 安全修法 / 答辩追问点 / 确认状态`
- 所有锚点、图片路径、图号、表号、证据链接是否仍然有效
- 页面是否把任何 `P0` 弱化成了“建议优化”
- 完整评审页 / 学生执行页 / 导师汇报页之间是否对同一问题给出了互相冲突的说法

如果图表问题是核心争议，记得同步加载 [figure-table-standards.md](./figure-table-standards.md)，把“图表是否选对类型”“图注是否完整”“论文图与答辩图是否分流”一并纳入检查。

## 6. 第三方建议 / 其他代理输出复核回复模板

当用户问“某个 reviewer / AI / 代理工具的建议对不对”时，用这个顺序：

1. 先给总判断：大体同意 / 部分同意 / 不同意
2. 再拆成：
   - 明确正确
   - 方向对但要改写
   - 过强、过度或不安全
   - 已经过时，因为当前版本已修复
3. 每个判断尽量回到原文、表格、图片或当前文件状态
4. 最后标清它应该归入：
   - `P0 / P1 / P2`
   - `Strategy`
   - `Upgrade`

如果建议来源是 `Codex`、`Claude Code`、`AntiGrativity` 或其他终端型代理，额外补一句：

- “以下判断已回查原文、图表和当前工作区文件，不把代理输出本身视为最终证据。”

如果过程跨了多个线程或工具，额外补一句：

- “本轮过程摘要已压入 `process_projection`；以下结论以当前真源和证据型中间文件为准，不以聊天顺序本身为准。”

如果输出进入导师式逐条改稿模式，额外补一句：

- “以下改写建议均绑定到当前可见证据；需要原始数据、代码或批件才能安全落笔的句子，已单列为待人工回查。”

## 7. 答辩口径小模板

以下句式可作为安全起点，再根据论文实际情况改写。

### 开放标签局限

“由于干预形式差异明显，本研究未能实施受试者和治疗师盲法，因此应界定为开放标签研究。该设计可能提高主观结局的偏倚风险，后续研究应进一步补充独立评估者盲法或录像盲评方案。”

### 探索性机制结果

“影像学结果应理解为探索性机制线索，而非对疗效机制的确证性证明。”

### 靶点不完全闭合时的安全表述

“尽管部分结局更偏向整体吞咽表现而非纯粹口腔期金标准，但口腔运动功能评分与相关表面肌电指标仍提供了与靶点更贴近的支持性证据。”

### 强但安全的结论

“本研究结果提示该方案具有潜在临床优势，但仍需在更大样本、标准化评估和更严格盲法条件下进一步验证。”

## 8. 交稿前终检模板

把它放在清单或 HTML 的末尾。

### 一致性检查

- 摘要、方法、结果、表格、图注里的样本数是否统一？
- 所有等级资料是否都改成了匹配的数据呈现？
- 每个“见图 / 见表”是否都指向正确对象？
- 图号是否唯一？中英文图题是否同步？
- 表格、图形、正文是否讲的是同一套统计口径？

### 方法和合规检查

- 研究身份是否诚实写清：随机、开放标签、探索性、pilot 或其他？
- 伦理审批和知情同意是否放在了标准位置？
- 注册状态是否准确交代？

### 解释边界检查

- 机制宣称是否没有超过证据？
- 探索性结果是否被明确标成探索性？
- 未来研究建议是否和已完成工作分开？

### 项目卫生检查

- README、CHANGELOG、实际目录结构是否一致？
- HTML 图片路径、锚点、统计指标是否仍然有效？
- 是否存在复制残留、控制字符、死链、旧版本路径？

### 交付物自审

以上终检查的是论文和项目文件。如果需要同时验证审查报告本身的准确性（引用是否对、分级是否一致、多份交付物是否同步、红线是否守住），加载 [self-audit.md](./self-audit.md)。

## 9. 高回报增强项

在 `P0 / P1` 收口后再考虑这些：

- 闭环机制概念图
- 小样本个体配对图
- 关键通道 / 关键连接的视觉强化
- 更好的答辩叙事弧
- 一段明确指出研究真正贡献的话

当增强项涉及图表时，优先考虑：

- 小样本个体图替代纯柱状图
- 关键通道 / ROI 高亮
- 完整但简洁的图注与表注
- 论文图与答辩图分开准备

对以下增强项要谨慎：

- 新补相关性分析
- 新补影像差值图
- 跨研究效应量对比
- 跨实验定量桥接

只有在原始数据、方法和时间都支持时才做，不要为了“看起来高级”临时扩分析。
